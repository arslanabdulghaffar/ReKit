# Canonical evidence-to-kit case

Design recorded before implementation for approved Winning-Quality Block B1/B2.
Mission 06 remains open. This case performs no inference and does not qualify AMD.

## Provenance and scope

`canonical-evidence-to-kit-v1` is an explicitly synthetic, scripted demonstration.
It reuses the existing three returns, four physical component IDs, `standard-kit`
BOM, catalog revisions, and disposition policy from the original synthetic case.
Its fresh database is isolated from previous demonstrations and operator data.
Two body objects arrive together; two separate returns each contain one adapter.
The diagram images are created locally by a deterministic fixture renderer, not
captured from real returns or generated by a recognition model. Original image
bytes, SHA-256 values, image asset IDs, return and component associations, and
append-only evidence events remain traceable through the existing asset API.
No historical ABO photographs, model outputs, or independent review judgments are
attached to this inventory.

The second adapter has two ambiguous intake views. A deliberately incorrect scripted
operator assertion identifies revision B, which the existing standard-kit policy
rejects. A third original synthetic close-up explicitly labels revision A. The
scripted operator appends a correction that supersedes the B verification and
cites all three uploaded observations. Neither original evidence nor the earlier
assertion is rewritten. This is fixture-based human-workflow automation, not an
actual independent human verification or evidence that visual inspection proves
function or safety.

## Existing authority boundaries

The FastAPI workflow binds human roles, controls expected versions, stores
observations and human assertions, checks compatibility, and atomically reserves
inventory. Existing OR-Tools CP-SAT selects approved candidate dispositions.
Existing human-role approval and completion endpoints remain the only execution
authority. The case adds fixtures, evaluation orchestration, and a presentation
of existing calculations; it adds no schema, planner, policy engine, API route,
LLM authority, authentication bypass, or database migration.

Affected modules: new `evaluation/canonical_case.py`,
`evaluation/run_canonical_case.py`, `evaluation/fixtures/canonical_case.json`, and
focused backend tests. The browser runner may select this identified fixture and
reuse its image renderer; existing replay modes and original fixtures remain
available. Interface work follows successful API verification.

## Economic assumptions and comparisons

All figures below are invented scenario estimates in USD cents, not realized
revenue, savings, measured labor, accuracy, or AMD performance. The supplied pool
is exactly the same four verified components for every alternative. Every
complete alternative must pass the existing `evaluate_selection` validator,
including exactly one disposition per physical component, BOM/revision/condition,
capacity, demand, and disposition-policy constraints.

| Assumption | Value |
| --- | ---: |
| Rebuilt standard-kit sale estimate | 10,000 per kit |
| Rebuild labor | 30 minutes per kit |
| Rebuild other processing cost | 500 per kit |
| Labor capacity | 60 minutes |
| Standard-kit demand limit | 2 |
| Donor retention | 600 per body; 200 per adapter |
| Whole-return liquidation, body return | 8,000 gross; 5 minutes |
| Whole-return liquidation, adapter return 1 | 1,000 gross; 2 minutes |
| Whole-return liquidation, adapter return 2 | 1,500 gross; 3 minutes |
| Baseline labor rate | 25 per minute |
| Controlled changed labor rate | 200 per minute |

Arithmetic verified against actual CP-SAT and complete-alternative validation:

| Complete feasible decision | Gross recovery | Labor cost at 25/min | Processing cost | Retained noncash value | Modeled value | Increment versus retention |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Two rebuilt kits | 20,000 | 1,500 | 1,000 | 0 | 17,500 | 15,900 |
| Liquidate all three whole returns | 10,500 | 250 | 0 | 0 | 10,250 | 8,650 |
| Retain all four donor components | 0 | 0 | 0 | 1,600 | 1,600 | 0 |

Retention competes with recovery; it is not subtracted twice from the objective.
Whole-return liquidation allocates every member and cannot coexist with a rebuild
using that member. Raising **only** `labor_cost_per_minute_cents` from 25 to 200
changes the optimum from two rebuilds (7,000 under the changed rate) to
three whole-return liquidations (8,500). The API receipt checks that the scenario
identifier and every other problem field stay unchanged for this comparison.
The browser workflow creates a new scenario identifier and description for each
proposal; its comparison checks that every economic input, catalog/policy and
component evidence snapshot is unchanged except the labor rate. Those descriptive
metadata differences are not hidden as an identical full input hash. The original
baseline plan is the one approved for completion. Alternative and sensitivity
plans are never implicitly executed.

## Acceptance criteria

1. Run from a fresh disposable database through authenticated in-process HTTP;
   generate no network requests and load no model.
2. Upload original fixture PNGs through the normal image API; fetch and hash-check
   them, and include source associations in the receipt.
3. Show unresolved input, the incorrect B assertion and actual policy rejection,
   the additional A view, and the explicit superseding correction; preserve all
   original event payloads. Reject a stale expected-version correction.
4. Solve baseline and one-rate-change scenarios using existing CP-SAT and report
   actual status, selected actions, input hashes, and validated complete
   alternatives. Independently enumerate the tiny feasible candidate subsets in
   focused tests to check the claimed optimum.
5. Propose a competing baseline plan before approval; approve the chosen plan;
   reject the competing approval with HTTP 409 and prove the reservations remain
   unchanged with no completed kits yet.
6. Require explicit confirmation and exact reserved IDs for completion; reject a
   false confirmation, then complete each action and verify idempotent retry.
7. Record two completed kits, four uniquely consumed components, all three source
   returns, verification/evidence versions and provenance, and the expected
   proposed/approved/two-completions audit history.
8. Remove temporary credentials, database, and working image copies. Retain the
   exported nine original PNGs and nonsecret receipt for owner review; they are
   separate from disposable application state. Preserve historical AMD receipts,
   attempt ledger, original fixtures, and NVIDIA configuration.

The recording should identify the whole segment as synthetic and scripted. A
separate real-image inspection segment must retain its actual local-NVIDIA label.

## Verified API receipt and reproducible replay

The first API run passed before interface changes. It retains a review receipt
and all nine original PNGs at the ignored local path
`var/mission06-offline/canonical-case-b1-first/`. Its `receipt.json` includes
original bytes' hashes and asset metadata, before/after correction histories,
complete immutable planning inputs, three alternative allocations per scenario,
reservation and final inventory snapshots, completed-kit lineage, and the four
baseline execution audit events. The store and temporary token were removed;
the export contains no database or credential material. The original baseline
fixture is unchanged.

```powershell
.venv\Scripts\python.exe -B -W error evaluation/run_canonical_case.py --output var/mission06-offline/canonical-case-review-NEW
.venv\Scripts\python.exe -B -W error -m pytest -q tests/backend/test_canonical_case.py
```

Choose a new output directory for each run. The exporter refuses to overwrite an
existing receipt. Without `--output`, the script prints the complete JSON
receipt and retains no generated files.

Actual API results: nine original images, three returns, four components,
`OPTIMAL` 17,500 cents for the baseline, `OPTIMAL` 8,500 cents after the sole
labor-rate change, two completed kits, four uniquely consumed components,
HTTP 409 for stale correction/stale plan/double allocation, and HTTP 422 for
completion without confirmation. Focused tests: **9 passed in 3.81 seconds**,
including independent exact-cover enumeration of candidate subsets for both
economic scenarios. Neither a real human assessment nor a physical kit rebuild
was performed. Browser replay and screenshots are separate acceptance evidence.
